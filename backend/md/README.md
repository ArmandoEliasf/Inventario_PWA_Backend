# Registro técnico — Fase de base de datos (Módulo Inventario PWA)

> Documento generado el 2026-11-11. Describe de forma técnica todo lo implementado
> en la fase de migraciones, modelos, observers y seeders del backend Laravel 12.

## 1. Contexto

- Proyecto: backend del módulo de inventario para una PWA (Laravel 12, PHP 8.2+).
- Origen del esquema: `database/bd-datos reales.sql` (dump PostgreSQL, ~2,300 líneas,
  con datos reales del clasificador de bienes de la UTC).
- Base de datos activa: SQLite local (`database/database.sqlite`), pendiente migrar a
  Supabase (PostgreSQL 18). El driver Eloquent mantiene compatibilidad con ambos.
- Herramientas: Laravel Artisan, Composer, Bruno (pendiente de colección), Pint, PHPUnit.

## 2. Análisis del esquema origen

El dump PostgreSQL contiene 24 tablas organizadas en niveles:

| Nivel | Tablas |
|---|---|
| Catálogos (0) | `area`, `tipo_profesor`, `roles`, `persona`, `usuarios`, `edificio`, `tipo_aula`, `tipos_bien`, `marcas`, `motivo_de_movimiento`, `adscripcion` |
| Referencias (1) | `profesor`, `alumnos`, `aula`, `familias_articulos`, `modelos`, `adscripcion_persona` |
| Referencias (2) | `articulos` |
| Núcleo | `bienes` (tabla central del inventario) |
| Operaciones | `auditorias`, `auditoria_detalle`, `prestamos`, `bitacora_movimientos`, `folio_siia`, `numero_resguardo` |

Elementos relevantes del SQL:

- Convención de claves primarias: `cve_<entidad>` con `GENERATED BY DEFAULT AS IDENTITY`
  → portado a `$table->id('cve_...')`.
- Tipos `SMALLINT` → `unsignedSmallInteger`, `DECIMAL(10,2)` → `decimal()`,
  `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` → `useCurrent()`.
- Dos triggers plpgsql que **no** se portan a la BD sino a la capa de aplicación
  (ver §5 Observers).
- Bloque `DO $$ ... $$` de poblado con lógica imperativa → replicado como seeder.
- Inserts con `SELECT ... WHERE ... ORDER BY random()` → reemplazados por generación
  determinista en el seeder (reproducibilidad del ambiente demo).

## 3. Migraciones

Archivos (`database/migrations/`):

1. `0001_01_01_000000_create_users_table.php` — **modificada**. Sustituye la tabla
   `users` por el esquema del dump:
   - `roles` (`cve_rol` PK, nombre UNIQUE, descripcion, fecha_alta)
   - `persona` (`cve_persona` PK, nombre, apellidos, cve_carrera, cve_nivel_estudio, fecha_alta)
   - `usuarios` (`cve_usuario` PK, usuario UNIQUE, contrasena_hash, FK cve_rol → roles,
     FK cve_persona → persona, email, activo, fecha_registro, fecha_actualizacion)
   - Se conservan `password_reset_tokens` y `sessions` (Laravel).
2. `2025_01_01_000001_create_catalogos_base_table.php` — `area` (auto-referencia
   `cve_area_padre`), `tipo_profesor`, `edificio`, `tipo_aula`, `tipos_bien`,
   `marcas`, `motivo_de_movimiento`, `adscripcion`.
3. `2025_01_01_000002_create_organizacion_table.php` — `profesor` (FK persona,
   tipo_profesor, area), `alumnos` (FK persona, matrícula), `aula` (FK edificio,
   tipo_aula, profesor, adscripcion; `codigo_barras`/`codigo_qr` UNIQUE), `adscripcion_persona`.
4. `2025_01_01_000003_create_inventario_table.php` — `familias_articulos` (FK tipos_bien),
   `modelos` (FK marcas), `articulos` (clave UNIQUE, FK familia), `bienes` con todos los
   campos del dump: `codigo_barras`, `nfc`, `codigo_qr`, `no_serie`, `no_factura`
   (todos UNIQUE nullable), `foto_url`, `foto_drive_id`, FKs a `modelos`/`articulos`/
   `aula`/`persona` (encargado), `costo_unitario DECIMAL(10,2)`, `estado_fisico`,
   `estado_prestamo` (default `disponible`), `activo`, `fecha_registro`, índice `idx_bienes_qr`.
5. `2025_01_01_000004_create_operaciones_table.php` — `auditorias`, `auditoria_detalle`,
   `prestamos` (estados: `pendiente`, `aprobado`, `por_devolver`, `devuelto`),
   `bitacora_movimientos`, `folio_siia`, `numero_resguardo`.

Orden de ejecución garantizado por dependencias FK. Todas las FKs usan
`constrained()` con claves personalizadas.

## 4. Modelos Eloquent (`app/Models/`)

24 modelos. Convenciones:

- `protected $table` y `protected $primaryKey` explícitos (nombres `cve_*`).
- `$timestamps = false` salvo `Usuario` (mapea `fecha_registro`/`fecha_actualizacion`
  vía constantes `CREATED_AT`/`UPDATED_AT`).
- `$fillable` completo según el esquema.
- `Usuario` extiende `Illuminate\Foundation\Auth\User` con `getAuthPassword()`
  devolviendo `contrasena_hash` (preparado para autenticación futura).
- Relaciones implementadas: `belongsTo`, `hasMany`, `hasOne`, `belongsToMany`
  (ej. `Persona::adscripciones()` pivot `adscripcion_persona`), auto-referencia
  (`Area::padre()`/`Area::hijos()`).

Estructura de llaves de los modelos: `BienObserver` y `PrestamoObserver` se registran
por atributo `#[ObservedBy([...])]` (Laravel 12) en lugar de `AppServiceProvider`.

## 5. Observers (`app/Observers/`) — reemplazo de triggers

| Trigger original | Reemplazo |
|---|---|
| `trg_actualizar_estado_prestamo` (AFTER UPDATE ON prestamos) | `PrestamoObserver::updated()` — si `estado_prestamo` cambió: `aprobado` → `bienes.estado_prestamo = 'prestado'`; `devuelto` → `'disponible'`. Guardas: `isDirty()` y query dirigida con `whereKey()` (evita recursión de eventos del modelo `Bien`). |
| `trg_log_estado_fisico` (AFTER UPDATE ON bienes) | `BienObserver::updated()` — si `estado_fisico` cambió, inserta en `bitacora_movimientos` con motivo "Revisión de Inventario" (lookup por nombre, fallback id 1), persona `COALESCE(cve_encargado, 1)` y observación `El estado físico cambió a: <estado>`. |

Decisiones:
- Los triggers viven en la capa de aplicación → portabilidad total entre SQLite/PostgreSQL.
- `PrestamoObserver` actualiza `bienes` con query builder (no Eloquent `update()` del
  modelo) para no disparar `BienObserver` innecesariamente.

## 6. Extracción de datos (`database/seeders/data/catalogos.php`)

Script temporal `extract_sql_data.php` (en directorio temporal, no versionado) que:

1. Localiza todos los `INSERT INTO <tabla> (...) VALUES (...)` (incluye `preg_match_all`
   para los 19 bloques de `articulos` y el patrón `SELECT a.* FROM (VALUES ...)` de `aula`).
2. Tokeniza filas respetando comillas y paréntesis anidados (maneja `''` como escape,
   `TRUE/FALSE/NULL`, y subselects `(SELECT cve_... FROM ...)`.
3. Descarta filas del bloque `DO` que contienen identificadores PL/pgSQL
   (`id_persona_admin`, etc.), marcadas como `__ident`.
4. Exporta a PHP vía `var_export` → `database/seeders/data/catalogos.php`.

Filas extraídas: `area` 15, `tipo_profesor` 15, `roles` 4, `persona` 27, `usuarios` 11,
`edificio` 25, `tipo_aula` 15, `tipos_bien` 2, `marcas` 25, `motivo_de_movimiento` 15,
`adscripcion` 38, `familias_articulos` 16, `modelos` 25, `articulos` 1592, `aula` 27.

## 7. Seeders (`database/seeders/`)

### `CatalogosSeeder`
- Inserta los catálogos del dump en orden de dependencias.
- Resuelve subselects (`__raw`) en tiempo de seed:
  - `tipos_bien WHERE clave = 'X'` → familias
  - `familias_articulos WHERE clave = 'X'` → artículos
  - `adscripcion WHERE clave_adscripcion = 'X'` → aulas
- Genera los `INSERT ... SELECT` del dump como código:
  - `profesor`: personas 1–5 y 16–20 (tipo 1, área 1).
  - `alumnos`: personas 6–15 y 21–25, matrícula `MAT-XXXX`.
- `adscripcion_persona`: vinculaciones hardcodeadas (nombres ↔ claves de adscripción,
  9 grupos) tomadas del `INSERT ... SELECT` con OR del dump.

### `InventarioDemoSeeder`
Replica el script de presentación (~100 bienes de DSM):
- Distribución de aulas por rango: A-101 (1–17), A-102 (18–34), Lab-1 (35–51),
  Lab-2 (52–68), CC-1 (69–84), CC-2 (85–100).
- Encargados por rango: 1–20 admin, 21–40 director, 41–60 profesor, 61–80 alumno,
  85–100 Jorge (DSM).
- Códigos generados: `BAR-NNN`, `NFC-NNN`, `QR-NNN`, `SN-NNN-NNN`.
- `estado_fisico` `regular` si `rn % 5 == 0`, si no `bueno`.
- `estado_prestamo` `prestado` en los mismos rangos del dump (1–4, 22–25, 41–44,
  61–62, 85–86) con préstamos `aprobado` asociados + 2 `pendiente`.
- Bitácora (5 movimientos admin + 3 profesor), 2 auditorías, resguardo y folio SIIA
  por bien (`RGTO-NNNN-YYYY`, `SIIA-NNNN`).
- Totales: 100 bienes, 18 préstamos, 100 resguardos, 100 folios.

### `DatabaseSeeder`
Orquesta: `CatalogosSeeder` → `InventarioDemoSeeder`.

## 9. Incidentes corregidos durante la fase

1. **BOM UTF-8**: archivos generados con PowerShell 5.1 incluían EF BB BF inicial →
   fatal "Namespace declaration..." en PHP. Limpieza de BOM en todos los modelos/seeders.
2. **Import faltante de observers**: `#[ObservedBy]` sin `use App\Observers\...`
   resolvía `App\Models\BienObserver` → "Unable to find observer". Corregido con imports.
3. **Parser del SQL**: strings truncados (comilla de cierre no conservada), primera
   iteración solo capturaba 1 de 19 bloques de `articulos`, y el tokenizer separaba
   valores antes de filtrar filas con identificadores del bloque `DO`.

## 11. CRUD de bienes — pautas y implementación

### 11.1 Pautas acordadas

| Regla | Definición |
|---|---|
| Código de barras | `{TIPO}-{FAMILIA}-{ARTICULO}-{IDENTIFICADOR}` — ej. `MO-MD-1583-0000001`. Se arma con las claves de tipo de bien, familia y artículo del catálogo, más un identificador numérico de **exactamente 7 dígitos** que pone el usuario (se guarda como string para conservar ceros iniciales). |
| Identificador = no_serie | El identificador que captura el usuario **llena la columna `no_serie`** (UNIQUE → unicidad global del identificador). La API no expone `no_serie` como campo propio: se devuelve como `identificador`. |
| Código QR | Generado automáticamente al crear: en BD se guarda `bienes/{cve_bien}`. La URL completa se construye en runtime con `FRONTEND_URL` del `.env` (config `services.frontend.url`), ej. `http://localhost:5173/bienes/5`. Cambiar de dominio solo requiere editar el `.env`. |
| Roles | Administrador: todo. Profesor: crea/edita/papeleriza **solo sus propios bienes** (donde `cve_encargado` = su persona). Alumno (rol Estudiante): no consulta ni modifica el inventario. |
| Registro de usuarios | Fuera del alcance de la API: lo hace el área de programación directamente en la BD. |
| Papelera | Eliminar = `activo=false` (nunca delete físico). Bloqueado si `estado_prestamo != 'disponible'`. Registra bitácora con motivo "Baja Definitiva". |
| Estados físicos | `bueno`, `regular`, `deteriorado` (constante `BienesService::ESTADOS_FISICOS`). |

### 11.2 Archivos

- `app/Services/CodigoBarrasService.php` — construcción del código de barras
  (artículo → familia → tipo) y verificación de unicidad.
- `app/Services/BienesService.php` — lógica de negocio: `listar`, `obtener`,
  `crear`, `editar`, `enviarPapelera`, `urlQr`, helpers de rol
  (`rolDe`, `esAdmin`, `esProfesor`, `puedeConsultar`).
  - En `crear()`: profesor queda como encargado; admin puede asignar
    cualquier `cve_encargado`. QR se inserta con `saveQuietly()` (sin eventos)
    dentro de transacción.
  - En `editar()`: si cambia el artículo se re-genera el prefijo
    TIPO-FAMILIA-ARTICULO conservando el identificador; unicidad excluye al propio bien.
  - `enviarPapelera()`: transacción + bitácora (motivo "Baja Definitiva").
- `app/Http/Requests/StoreBienRequest.php` / `UpdateBienRequest.php` —
  validación del identificador (`regex:/^[0-9]{7}$/`), unicidades de
  `no_serie`/`no_factura`, exists de FKs, estados físicos permitidos.
- `app/Http/Controllers/BienController.php` — endpoints del `apiResource`.
  Resuelve el actor con el **header temporal `X-Usuario`** (cve_usuario)
  porque aún no existe autenticación; marcar `TODO` para cambiar por
  `$request->user()` con Sanctum.
- `app/Http/Resources/BienResource.php` — serialización con catálogos cargados.
- `routes/api.php` — `apiResource bienes` (index, show, store, update, destroy).
- `bootstrap/app.php` — se registró `api: routes/api.php`.
- `config/services.php` + `.env` — `FRONTEND_URL` (default `http://localhost:5173`).

### 11.3 Endpoints

| Método | Ruta | Descripción |
|---|---|---|
| GET | `/api/bienes?per_page=20` | Listado paginado (profesor: solo suyos; admin: todos; alumno: 403) |
| GET | `/api/bienes/{cve_bien}` | Detalle + `qr_url` completa para pintar el QR |
| POST | `/api/bienes` | Crear (requiere `cve_articulo`, `nombre`, `identificador` de 7 dígitos) |
| PUT/PATCH | `/api/bienes/{cve_bien}` | Editar (re-genera código de barras si cambia el artículo) |
| DELETE | `/api/bienes/{cve_bien}` | Papelera (solo bienes `disponible`) |

Todos requieren header `X-Usuario` (temporal hasta implementar auth).
